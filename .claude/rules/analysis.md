# `internal/analysis`

The core engine: `engine.go` (`Engine.Run`, context sizing), `run_state.go` (the `runState` a run collects across files, and each file's `fileResult`) and `file_check.go` (`Engine.checkFile`, one file's flow as `fileCheck` methods).

## Content providers

`ContentProvider` abstracts *which* files to scan and how to read them: `UncommittedProvider` (default), `StagedProvider` (`--staged`), `AllProvider` (`--all` or a `.` path arg), `MultiFileProvider` (one or more explicit path args), `ChangedSinceProvider` (`--since <ref>`: files that differ between the ref and `HEAD`, judged by their diff; see `docs/arch/0030-judge-the-change-under-since.md`).

## Per-file flow

`Engine.Run` fans out over files with a bounded worker pool (`analysis.max_concurrency`, default 5) via `errgroup`, running `checkFile` per file, then publishes the collected findings onto `Engine`. Per file: fetch context → strip unified-diff patch metadata (`stripDiffMetadata`, only when the content actually came from `GetDiff` — never applied to the whole-file-content fallback, since heuristically detecting "is this a diff" on arbitrary file content risks false positives) → build candidates (`VectorStore.ScopedADRs`, minus `archguard-ignore: <ADR_ID>` suppressions) → run the scoring stages (see below), where the default cosine stage takes its `topK` from `analysis.max_relevant_adrs` (default 3 when unset or `<= 0`) — see `docs/arch/0007-scope-filtered-before-topk-similarity.md` and `docs/arch/0020-configurable-topk-adr-limit.md` → call the LLM for each remaining ADR.

Outside `--debug`, `CosineRanker` calls `Search` with an unbounded `topK` (scope and threshold already applied) and the stage applies the top-K cut. In `--debug` mode it calls `VectorStore.SearchWithDebugInfo` instead, which derives `hits` and `rejected` from one query's candidate set (not independent calls to `Search`/`SearchRejected`/`SearchTruncated`) so rejected ADRs keep real scores; the stage prints each below-threshold ADR's title/score ("Below threshold") and each top-K-cut ADR's title/score/rank/qualifying-count ("Cut by top-K limit"), and `candidateSource` prints "Skipping ADR ... (Suppressed)" for every suppressed scope-matched ADR before them -- see `docs/arch/0009-debug-visibility-for-rejected-adr-candidates.md` (and its amendment for #190) for the diagnostic format, and `docs/arch/0019-single-query-consistency-for-debug-diagnostics.md` for why the three independent-query approach was replaced.

## Scoring pipeline (`internal/analysis/stage`)

A `stage.Scorer` returns one score per `Candidate` for a file, on the scale of its stage's `Threshold` (0-1 for screening models, raw cosine similarity for `CosineRanker`), for all candidates in one call, given a `File` and a `Debug`; a `stage.Stage` wraps a scorer with a `Threshold` (minimum score, optionally per ADR) and `MaxKeep`, dropping, ordering, and cutting by score. `Engine.Stages` defaults to one `stage.NewCosineStage` around `CosineRanker` (`cosine.go`); `cli.runCheck` overrides it with `analysis.BuildStages` (`stages.go`) when `analysis.pipeline` is set and gets nil otherwise, so no block means the default. `BuildStages` gives `rank` the legacy fallbacks (`vector_store.similarity_threshold`, `analysis.max_relevant_adrs`) and `rerank` a threshold of 0 and `top_k` of 3 with a printed warning per unset key (to `human`, so stderr under `--format json`); a `rerank` alone runs after the default `rank`. `CosineRanker` owns the embed call (through `inference.Embedder`) and the store query. `candidateSource` builds each file's candidates from `VectorStore.ScopedADRs` (scope-matched, no embedding needed) minus `archguard-ignore`-suppressed ADRs, so suppressed ADRs never reach a scorer or occupy a top-K slot. A pipeline without `CosineRanker` makes no embedding calls, and a stage handed no candidates is not scored, so a file with no candidates makes none either.

A scorer failure surfaces as a `stage.Error` whose `Action` the engine prints (`generating embedding` for cosine) and whose `Kind` is `KindUnavailable` (the default: a dependency didn't respond) or `KindPreconditionNotMet` (the stage can't run, e.g. cosine with no embedding provider); by default the file is skipped, but a stage with `on_error: fail` (`Stage.FailOnError`, named by `Stage.Name`, `rank` or `rerank`) instead appends a `StageFailure` to `Engine.StageFailures`, stops that file's remaining stages, and lets other files run; `cli.runCheck` maps the failures to `ExitStageUnavailable` (6) or `ExitStagePrecondition` (7, which wins when both occur), ahead of `ExitDriftDetected`, and `--update-baseline` returns that code without writing the baseline; `check --format json` adds a `failures` array (omitted when empty); a failure loading candidates (for example Postgres unreachable) skips the file with `Error: loading candidate ADRs: <err>` under its header rather than passing it. The LLM remains the only source of violations. See `docs/arch/0022-candidate-scoring-pipeline.md`.

## Context sizing (`fetchContext`)

Counts the file against `llm.max_tokens` via `Engine.Chat`'s `CountTokens` — each provider counts using its own real tokenizer/backend rather than one hardcoded encoder (see `docs/arch/0002-provider-scoped-token-counting.md`). If it fits, uses the content whole; otherwise prefers a diff (if available) over truncation (`truncateToTokenLimit`), which estimates a byte cutoff and verifies/shrinks it via further `CountTokens` calls, guaranteeing the result stays within budget. **Smart Truncation** rolls truncated content back to the nearest preceding newline so files aren't cut mid-line. Under `--since`, `cli` sets `Engine.JudgeChange` and `fetchContext` returns the file's hunks instead (no hunks means the file is skipped silently); `fileCheck.locate` then checks the model's `quoted_code` against the parsed diff (`diff.go`, `locate.go`) and drops a finding that is only in unchanged context. `archguard-ignore` is read from the whole file there, since its header is outside the diff.

**CI Warn-Open policy**: in `--ci` mode, a file that had to be truncated produces a warning instead of running analysis on a possibly-incomplete context — avoids failing a pipeline on inconclusive input.

## Roles, caching and output

**`Engine.Chat` / `Engine.Embed`**: the engine takes each role separately (`NewEngine(cfg, store, chat, embed, ...)`): chat calls and token counting go through `Chat` (an `inference.Chatter`), embedding through `Embed` (an `inference.Embedder`).

**Caching**: LLM analysis results are cached in `.archguard/cache/<sha256>.json`, keyed by model name + ADR content + file content + system prompt + prompt template (`internal/cache`). A cache hit skips the LLM call entirely.

**`Engine.Out`/`Engine.JSONOutput`**: all per-file log text goes through `Engine.Out` (an `*output.Printer`; nil writes to stderr, with `Engine.Debug` as its debug flag). Each file prints as one `Group` headed by its path, so a file with nothing to report prints nothing, and the group is what `stage.Debug` receives, so scorers' debug lines land under the file too. Every run appends each new (non-baselined) violation to `Engine.CollectedViolations`, and `Violation.Annotation()` turns one into an `output.Annotation`, dropping `Line` when it counts lines of a diff the LLM saw rather than of the file (an unexported field, so not in the JSON). `cli.runCheck` builds `Out` over stderr for every `check` run, marshals `CollectedViolations` onto stdout under `--format json`, and sets `JSONOutput` so `Engine.CollectedStages` holds the `stage.Telemetry` totals (received, kept and time per stage, summed across files, one `stage.Stats` each) for the JSON `stages` array and `Engine.Coverage` for the JSON `coverage` object. See `docs/arch/0014-json-check-output.md`.

`Engine` also records the findings the reports are built from: `SkippedFiles` (including a file too large for a `--ci` run), `PartialFiles` (analyzed through a truncated view; a `--ci` run skips such a file instead), `FailedChecks`, `StageFailures`, `Baselined`, `Coverage` (an `output.Coverage`: files judged, ADR checks that returned a verdict, files with no relevant ADR; a skipped or partly checked file is in none of the file counts, and `Engine.checkFile` is where each file is counted) and, under `--update-baseline`, `RecordedEntries` and `UnrecordedViolations`. `Engine.Report()` and `Engine.BaselineReport(path)` turn them into `output.Report` and `output.BaselineReport`, which share `output.Gaps`; a new kind of gap is a new field there. Under `--debug` each ADR check logs one outcome line (`checkOutcomeLine`).

`Engine.SuggestFixes` (set from `check --suggest-fixes`, default off) makes one extra `inference.SuggestRemediation` call per newly-reported (non-baselined, non-`--update-baseline`) violation, caching the result under its own `cache.ComputeSuggestionKey`-derived key (independent of the judgment `AnalysisResult` cache entry) so it's reused free on a later run of the same file/ADR pair. See `docs/arch/0016-llm-suggested-remediation.md` and `docs/arch/0017-suggestion-cache-key-namespace.md`.

## Footguns

- **An already-cancelled context ends `Engine.Run` before any file is read**, returning `context.Canceled` with no files analyzed. See `docs/arch/0024-run-context-cancellation.md`, and `docs/standards/testing.md` for skipping retry backoff in a test.
- **The baseline file must stay excluded from analysis.** Once `archguard-baseline.json` is committed, it's git-tracked and enters `AllProvider`'s file list like any other tracked file; `Engine.shouldExclude` unconditionally excludes `baseline.Path` (not dependent on the user's `exclude_patterns`) because the file's own content is quoted violating source snippets — scanning it risks the LLM flagging the baseline file itself, which in `--update-baseline` mode would baseline a false violation into the file, changing its content, invalidating that entry next run, and re-surfacing it as new drift.
- **Suggestions are cached under their own content-addressed key/namespace, independent of the judgment `AnalysisResult` cache entry.** `cache.ComputeSuggestionKey` (model, ADR content, file content, reasoning, quoted code, `inference.SuggestionSystemPrompt`, `inference.SuggestionPrompt`) is a separate key from `cache.ComputeAnalysisKey`, stored via `Cache.GetSuggestion`/`PutSuggestion` under `.archguard/cache/suggestions/` rather than merged into the judgment entry. This means a future change to the suggestion prompt text naturally changes the key -- old suggestions simply become unreachable cache misses rather than needing manual invalidation -- while judgment cache entries (and a non-`--suggest-fixes` run's behavior) are completely unaffected by anything suggestion-related. See #167.
